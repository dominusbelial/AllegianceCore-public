# P928 allocation identity proof

`P928Trace.cs` is compiled into both this executable and `P928AllocationTests`.
The checked-in fixture was generated on the unmodified simulation at the base
revision recorded in `docs/reports/P928_REPORT.md`, before any allocation cut.
It must not be regenerated to accept an optimisation.

With artwork configured in the environment:

```sh
dotnet run --project tools/p928-allocation-proof -c Release -- replay.csv
dotnet test tests/Allegiance.Core.Tests --filter FullyQualifiedName~P928AllocationTests
```

The CSV holds 500 independent SHA-256 digests of binary, little-endian float
state, site callbacks in dispatch order, and encoded `SINGLE_SHIP_UPDATE`
packets, plus cumulative seeded RNG draws and per-tick event counts. The core
file SHA-256 is pinned in its header. No private artwork is included.

The deterministic one-sector scene uses 240 flying ships (12 following native
GotoPlan waypoints), 20 turret gunners, duplicate fixed/turret mounts, 8 sensor
probes, 12 mines, 12 asteroids, 2 stations, firing weapons and a sustained salvo.
The fixture pins sensor probes' initial attitudes before ticking. Weapon RNGs
use the existing injectable `Weapon` RNG, assigned by reflection because the
ordinary `MountWeapon` entry point does not expose that argument. These are
proof-only controls; production simulation has no new flags or hooks.

State coverage includes model order, ids, clocks, position, velocity, all nine
orientation floats, ship hull/shield/energy/ammo/fuel/control-state, weapon
firing state, visibility/eye bits, mine/probe/missile fractions, probe ammo,
retired/dead ships and live asteroid/station health. Ordered event coverage
includes collision callbacks, damage (full arguments), ship kills, projectile
creation and projectile impacts. The wire digest tests the real codec for
all living ships; it does not claim to capture server per-viewer scheduling,
visibility filtering, or transport framing. Existing broadcast identity tests
cover those paths.

The RNG counter covers seeded scenario and weapon dispersion draws. The
uncontrolled two draws in each sensor probe constructor are excluded because
the initial attitude is explicitly reset and the sensors never fire. The scene
avoids other unseeded production RNG paths (treasure, NPC complaints and chaff).

For allocation sampling (the measured performance comparison uses ordinary
NativeAOT binaries with server GC):

```sh
dotnet build tools/P835Bench -c Release
dotnet-trace collect --profile gc-verbose --output after.nettrace -- dotnet tools/P835Bench/bin/Release/net10.0/P835Bench.dll 400 240 60
dotnet run --project tools/p928-allocation-proof -c Release -- --allocations after.nettrace
python3 tools/p928-allocation-proof/summarize.py .scratch/p928 final
```

`AllocationReport` groups sampled allocation bytes by type and first application
stack frame, including startup/warmup. It lists all groups, in descending order,
so the report can show the top ten without hiding the remainder. These are
sampling estimates, not exact object counts. NativeAOT's default build disables
EventSource; a separate `-p:EventSourceSupport=true` diagnostic publish permits
a GC capture, but the tested runtime emits NULL allocation type names and no
resolved application frames. Use the companion JIT capture for site attribution,
and the default NativeAOT binaries for the before/after performance numbers.

The original fixture is preserved unchanged. A supplemental 500-tick fixture
adds projectile headings/lifetimes, full controls/turn rates, ore/cloaking,
parent/dock IDs, static-body geometry, weapon burst/mount state, and station /
expendable callbacks. It was generated by temporarily restoring the exact base
Core source files (and removing the new scratch partial), verifying the original
fixture still matched byte for byte, recording the supplemental fixture, then
restoring all cuts. The report's fixture provenance JSON records source and
fixture hashes. `--supplemental output.csv` runs this additional serialization;
it does not alter scenario inputs or the original fixture format.

The local NativeAOT server capture can be repeated using `showcase.py before
150 1` then `showcase.py after 150 1`, repeated for runs 2 and 3. It launches only
local processes, uses an ephemeral loopback port, requests 60 bots per side,
checks the spawn receipts, and writes existing `[gcprof]` / `step:` output to
scratch. No deployment configuration or host outside this machine is changed.
