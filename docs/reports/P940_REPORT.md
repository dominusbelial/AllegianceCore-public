# P940 — Basic Flight through real window input

Basic Flight now completes through real input in both HUD styles; its final narrated cohort passed ten fresh windows per style. The investigation found five production port defects in addition to the native, intentional control locks, plus an unreliable Target Practice proof pilot and gaps in older loopback test drivers exposed by the corrected execution path. Changes are left in the working tree; no commits, pushes or remote-host operations were performed. The executable proof is `tools/p912-training-proof`, driven by `Game1.TrainingProof.BasicFlight.cs` and selected by the two Mission 2 cases in `P912TrainingWindowTests.Every_lesson_completes_in_one_real_window_session`.

The pilot supplies keyboard and mouse states to the existing input seams. It never completes a goal, relocates an actor, supplies an applied control/state bit, changes a lesson condition, accelerates the clock, or rebinds a prompted key. The observer reads the actual post-filter command and local physics, checks all nine lessons, the five exact native prompts in order, real docking at station 1010, native session completion and the post-mission slideshow. Keyboard and mouse turn probes, throttle presets/steps, both physical backslash key variants, actual wheel notches and SPACE all use the shipping handlers. There is a stop/release between the two backslash probes so a previously full throttle cannot conceal a broken alias.

## Defects and regression evidence

1. **Forced throttle survived the demonstration.** Goal 6.9 called the throttle-preserving spin helper, whereas native executes an empty `SetControlsAction` at `mission2.cpp:585-590`. It consequently forced 0.33 even after all four player axes were enabled. The mission now clears all forced controls. `TrainingMission2Tests.Motion_demo_clears_forced_throttle_before_all_axes_are_reenabled` fails with the previous action: expected NA, actual 0.330000013. The real-window assertion also rejects the old action at 6.9 (raw full throttle, applied −0.33999997).
2. **The displayed SPACE booster instruction did not operate the booster.** `TrainingInputGate` recorded native TK_FireBooster, but flight translation consulted only the normal Shift binding. The former pilot concealed this by pressing Shift alongside SPACE. The shared `BasicFlightBoosterDown` handler now recognizes the native key in Basic Flight while retaining the key gate's rejection state. Native: `WinTrek/WinTrek.cpp:10878`, `training/mission2.cpp:725-748`. Reverting it fails both the SPACE action case and the rejected-until-release case; Shift and ordinary non-training behavior remain covered.
3. **Installed narration was silently rejected.** `SoundEffect.FromFile` accepts WAVE, but the fallback passed it the artwork's Ogg Vorbis clips and swallowed the resulting `ArgumentException: Specified stream is not a wave file.` Training voices now decode through the already installed NVorbis 0.10.4 dependency into PCM (declared explicitly on the shared library so Android receives it too), cache the owned sound asset and dispose it with the sound manager. Instances retain ordinary playback/finish state. Native playback and completion: `training/playsoundaction.cpp:35-43`, `training/soundfinishedcondition.cpp:33-43`, `training/trainingmission.cpp:896-902`. The production-loader regression returns null with the old loader and passes with the decoder; the PCM test checks non-silence, original sample count, rate and channels.
4. **Connected Basic Flight retained an extra movement owner.** The old host autopilot pass nudged positions even for zero elapsed time. Connected M2 now uses the same simulation-owned NPC plan path as the other connected training lessons. Basic Weaponry shares its `training_1` / sector-1010 universe (`training/mission3.cpp:88-90,163`), so connected M3 follows this path too; the broader training gate exercises both styles. `Connected_basic_flight_has_one_physics_owner_and_never_nudges_at_zero_elapsed_time` waits through an ordinary intro-length idle period, then requires no movement on ten zero-duration updates and actual velocity/movement with positive elapsed time. Reverting the host change moves the commander from `(500,0,0)` to approximately `(458,-12,24)` without advancing time. Native mission commands and simulation execution: `training/mission2.cpp:232-239`, `Igc/shipIGC.cpp:2795-2807`.

Raw investigation and negative controls are retained under `.scratch/p940/`, including `negative-controls/`. The negative-control group has four failing and four passing input/audio/host cases; the separate motion-reset case fails once. The frame-ownership negative control also fails, explicitly observing current=700 with an empty accepted slot. The final fixes were restored after each negative control.

5. **A host tick could split the native action list.** The narrated paired replay left one commander stationary with all command slots empty and a zero-consumer waypoint, while the other reached the unchanged radius check. `TrainingSession.Start` and `Advance` now share the host simulation lock for the whole frame, keeping the existing client-before-host lock order. ## Forum reply

Basic Flight deliberately unlocks steering and throttle in stages, so having only thrust respond during the throttle lesson is expected. We also found tutorial bugs affecting the throttle reset, the prompted SPACE booster key and spoken instructions, and corrected them; Basic Flight now has a real-window completion test in both HUD styles.

## Native intent

**Design:** staged locks, instructor-controlled demonstrations, SPACE acknowledgements, reminders, and autopilot landing are native lesson behavior. **Era constraint:** narration and sequential scripted goals explain when controls become available; with missing narration the player loses that explanation. **Bug:** retained forced throttle, a prompt key that cannot activate its action, rejected installed audio, a second position integrator and an interleaved mission action list are production port defects. The M3 aiming/firing and older loopback-driver corrections repair automated input/facility strategies; native gameplay conditions are unchanged. A Modern-only on-screen indication of the currently unlocked controls would improve clarity, but this task preserves the native behavior and adds no new HUD design.
