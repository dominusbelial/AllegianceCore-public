# PERF-R1 — AllegianceCore dedicated server at 200v200

Base `aa34d1e0` (v0.1.8). **Read** means observed in this revision or, where identified as historical, in a prior report. **Measured** means observed locally for this review. **Estimated** means a work bound or hypothesis. No candidate optimization has been timed.

In the source references below, unprefixed server files are under `src/Allegiance.Server/`, `Core/` expands to `src/Allegiance.Core/`, and test names refer to files under `tests/`. Native references name paths under the original Allegiance source tree.

## Five priorities

**1. Reuse the visibility work the ranked sender has already done.** In the optimized 400-viewer replay, ranked HEAVY/LIGHT projection took 9.66–9.82 ms of a 12.71–12.87 ms mean projection and flush. The 2 Hz floor already requires an ordered visible list for every viewer. Ranking checks the same candidates again, and the floor revisits large dictionary values by ship ID. At full co-location, fusing the candidate walks can remove about 160,000 visits per tick while retaining every viewer's own floor and every deviation mutation. The 9.7 ms is the whole stage, not a saving estimate. `Server.RankedPose.cs:36–86`, `Server.UpdateCadence.cs:180–229,363–388`.

**2. Reuse the parallel teammate builder's per-viewer results.** This was the largest allocation bucket in the optimized replay, approximately 72.4–72.6 MiB over 200 ticks. A quiet viewer still gets a new result, three lists, three sets, three dictionaries and two local overlay sets before the first teammate is tested. A 400-player game therefore constructs at least 4,800 such objects per tick, excluding backing arrays. Reusing or lazily allocating this scratch leaves the worker partition and ordered application of effects intact. `Server.Broadcast.cs:1373–1408,1419–1443,1478–1494`.

**3. Reduce fallback scanner work on visibility ticks.** With 400 verified living ships and native crowding, the first sweep in each short battle had a conditional p95 of 3.71–11.99 ms across three local runs. On a separate sustained workload with crowding damage disabled, due-sweep p95 was 12.06–12.83 ms. The current code tests the remembered spotter correctly, then walks scanners in order until it finds a witness or exhausts the list. Measure fallback lengths, range rejection and rock tests before trying a conservative spatial index. A candidate must reproduce the winning spotter and every discovery/score edge, including flag carriers. `Core/Model/Sector.cs:1232–1242,5544–5576,5613–5637`, `Core/Sim/VisibilityMath.cs:83–93,124–156`.

**4. Skip impossible rescue pairs.** The sector builds the flying-ship list and checks every unordered pair even when every ship is a fighter. At 400 fighters that is 79,800 pairs with no possible rescue. The rescue group averaged 0.21–0.25 ms on the verified living/native sample and 0.34–0.49 ms in the sustained sensitivity run. During the existing gather, detect whether any pod and any eligible non-pod rescuer exist. With both present, keep the entire ordered path. This leaves collision-triggered rescues and the proximity fallback in place. `Core/Model/Sector.cs:1181–1210,1410–1445,3688,3716–3731`.

**5. Remove the second ordering of the ranked prefix.** Each viewer drains a min-heap ordered by (deviation, negative insertion ordinal), then sorts the same K records into exactly the reverse of that order. Walk the drained prefix backwards before visiting unserved candidates. This is a small, separately testable CPU cut within the largest measured stage. It preserves the sequential dependence of later viewers on earlier viewers' updates. `ShipUpdateRanking.cs:16–34`, `Server.RankedPose.cs:56–68`.

### Baseline and acceptance

**Read, historical.** The control is the 195v195 march used to represent 200v200. Use the showcase map, dedicated sizing, immutable snapshot, encode-once, native ship updates, parallel builders, pooled TCP writers, native GotoPlan, server GC and auto time dilation. The documented b55 median was 16.2 ms, window p95 about 20 ms, worst GC pause 36 ms at 394 connections. The older clash estimate of roughly 220 MB/s and ten gen0 collections/s belongs to a different build. The README calls for 2,048 connections and a per-source cap of 1,024 for this test. Current code also defaults the ship-status change gate and gunfire batching on. Record resolved boot flags, worker counts, floor and telemetry settings with each control. `README.md:243–319`, `ServerConfig.cs:857–911,1320`, `Server.UpdateCadence.cs:14–32`.

Every proposed change is an independent **default-off experiment** against that control. Compare paired, matched-population runs from march through contact, kills/relaunch and rotation. Use the P863 acceptance criteria of TiDi ≥0.95 in **every five-second clash window**, tick p95 ≤40 ms and p99 ≤50 ms. Keep per-peer output transcripts and gameplay outcomes alongside CPU, process-wide MiB/s, GC pauses, delivery age, queue depth and disconnects. Report pooled and worst-window tails separately. Ranks below estimate opportunity at peak, with allocation pressure and implementation confidence breaking ties. `docs/reports/P863_REPORT.md:4–7`, `docs/PERFORMANCE.md:17–48`.

### Reproduction and limits

Intel Core Ultra 9 285HX, 24 logical CPUs, Linux, .NET runtime 10.0.14, SDK 10.0.403, server GC. P835 uses seed 835, a fighter with scanner range 800, sustained low-damage rounds and 0.053 s increments. The tables distinguish its raw object counts from verified living populations. **Beyond the small changes.** Each option below requires its own diagnostic and parity replay before a production experiment.

- **Across-sector simulation.** Count busy sectors and concurrent runnable work *per chunk*. The optimistic simulation-only saving is the sum of sector times minus the largest sector time, before barrier/merge overhead. In a one-sector clash nearly all of that time remains. Movement, RNG, damage, warps and site callbacks can change objects another sector will read in the same pass. First trace those dependencies with simultaneous opposite-direction warps and a same-tick station death/rotation; parallelize only disjoint work or pure detection with an exact ordered commit. If reproducing immediate effects serializes the path again, stop. P667 cell-level parallel detection was already rejected. `Core/Model/Mission.cs:1089–1122`, `Core/Model/Sector.cs:1051–1061,1143–1165`, `docs/reports/P600_TICK_PROFILE_AND_PER_SECTOR_DESIGN.md:195–277`, `docs/reports/P858_DROP_REJECTED_FLAGS.md:5–23`.
- **Data layout and capture locks.** Count capture-gate entries, blocked time, selected HEAVY records, distinct ships, and effective viewer sectors. Each selected HEAVY takes the global gate even on a cache hit, yet a concentrated sector normally has one sequential ranking worker. Contention cannot be inferred from lock count. If lookup/lock cost dominates, precompute immutable quantized records by subject reference and pass them to workers in ordinal storage. Preserve the observer-relative write and exceptional parent/target cases. The group key uses the peer's physical sector while an administrator can view another sector. Verify disjoint ownership or use the original route for overlapping viewed sectors. A sector-wide precompute can lose on sparse visibility. `Server.RankedPose.cs:26–32,112–125`, `Server.Broadcast.cs:3101–3124`, `Server.Spectate.cs:78–88`, `Server.BroadcastSnapshot.cs:138–148,242–249`.
- **A different teammate broadcast model.** The next step after #2 is to schedule subject changes and audience catch-up explicitly. Count unchanged pairs that produce no packet, roster/loadout churn, missing per-peer knowledge and NPC refresh rates. A read-only ordered change list plus recipient-specific initial state could bring a quiet tick toward O(P + changes + deliveries). A cold join still costs the size of the roster. Keep own/export/status/loadout ordering, mission-local identities, queued repair/refresh and original slot order, including when the optional gate is off. Compare complete per-peer transcripts across late join, side switch, cloak, eject, restart and old/new object ID reuse. Native sends status on content change; the port already has P991 and a thin-client catch-up requirement. `Server.Broadcast.cs:1553–1657,1670–1708`, `Server.ShipStatusGate.cs:1–78`, `docs/reports/SHIP_STATUS_CHANGE_GATE_P991.md`.
- **Publisher and transport ownership.** Look at submit-to-send lag, stale drops, encoded bytes, time inside the gate, TCP partial writes, low-depth copy bandwidth and resident memory first. P968 already implements a default-off pending-stream index for multi-tick backlog. Use its existing switch if that condition is present. A future shared frame/lease across the transport boundary would save copies but requires one lifetime protocol across replacement, ordered delivery, async send, partial write, error, close and shutdown. The current snapshot lease has **one delivery** and returns after synchronous handoff. Do not attach it directly to an asynchronous queue. For WS, keep deadlines and physical memory bounded even when a pool rounds up buffers. `BroadcastSnapshot.cs:142–181,211–230,286–319`, `PooledPosePacket.cs:8–12,34–46`, `Core/Transport/TcpTransport.cs:1938–1956,2407–2451`, `Transport/WebSocketSendQueue.cs:22–50`, `docs/reports/PUBLISHER_STREAM_INDEX_P968.md:9–32`.
- **Server NPC steering.** Count server-controlled ships actually executing native GotoPlan, obstacle list sizes and scan time separately from human/client-driven seats. Two model scans plus rocks, stations and warps per active NPC can dominate an NPC-heavy sector. The list is already reused. If measured, try cached membership/immutable terrain values first and read mutable positions, velocities, ignore flags and death state at the exact original model-update instant. Require P817 native steering traces and ship-state/ordered event goldens. A single geometry snapshot at tick start can give later ships stale inputs. `Core/Sim/Ship.NativeGotoPlan.cs:31,85–91,396–433`, `Core/Model/Sector.cs:1049–1061`.
- **Reliable emission history.** The export sweep prunes all remembered viewer/source pairs every tick. During sustained gunfire the work can approach P·S and persist after guns stop, even with the P863 recipient cache. Measure live pair counts, removal rate, source/viewer churn and the prune-only time; the optimized fixture's entire export bucket averaged only 0.25–0.26 ms. If justified, invalidate by viewer/source changes and retain an ordered reconciliation path. Compare next-shot catch-up when the source hides, dies, warps, changes parent or reuses an ID; a stale remembered pose changes what the next recipient receives. `Server.Broadcast.cs:1827–1837`, `Server.FireAudience.cs:297–347,365–389`.
