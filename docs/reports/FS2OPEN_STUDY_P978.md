# P978 — FreeSpace 2 Open study: transferable ideas for AllegianceCore

**Status:** study and recommendations only. No implementation, gameplay test, performance run or remote-host access was performed. The read-only SCP checkout was at `d27de962b23c`; citations use the requested `fs2open:code/...:line` form. Native Allegiance means the read-only native source, cited by its source-relative path.

**License boundary:** this report discusses architecture, data shapes and algorithms in its own words. It contains no copied or closely paraphrased SCP implementation and does **not** recommend porting SCP code. SCP's Volition non-commercial notice and the later Unlicense notice are treated as a reason to take ideas only, never source.

**Reading key:** *parity-safe* means native-observable rules and information eligibility stay unchanged. *flag-only (non-parity)* means a default-off experiment may change behaviour or timing and needs explicit parity classification. *visual-only* means presentation alone changes; every such proposal has its own default-off `visuals.*` switch and retains the native path. “Cost” is engineering size unless GPU cost is stated. GPU statements below are design estimates, not measurements; the weak-iGPU target is the AMD UM690 class and the stress case is a single 200v200 clash.

## 1. HUD as data — feed P972, but keep its semantic core smaller than SCP

### 1.1 How SCP structures the HUD

SCP has three distinct layers that are worth separating conceptually:

1. **A registry of semantic gauge kinds.** Forty-two built-ins are filled in when a configuration omits them, while the parser also recognizes additional radar, weapon, flight-path and scripting variants (`fs2open:code/hud/hudparse.cpp:58-105`, `:148-205`, `:771-808`). A gauge object owns its resolved base dimensions, coordinates, font, colour/configuration state, view restrictions and optional custom art/text; 3-D-anchored gauges are explicitly a separate subclass that cannot slew (`fs2open:code/hud/hud.h:214-289`, `:392-410`). Thus identity/visibility/rendering remain typed even though placement is data.
2. **Resolution-selected layout records.** Each `#Gauge Config` can be default, named, or associated with one or more ship classes. It has a base resolution, optional minimum/maximum resolution and aspect filter, then an ordered gauge list (`fs2open:code/hud/hudparse.cpp:442-516`, `:584-723`). The base table is followed by `*-hdg.tbm` modules, and omitted retail gauges are replenished (`fs2open:code/hud/hudparse.cpp:752-808`). Aspect adjustment expands one base dimension rather than stretching X and Y independently; normalized origin plus pixel offset is an alternative to an absolute position (`fs2open:code/hud/hudparse.cpp:1380-1407`, `:1437-1475`). A second adjustment accounts for the centred viewport and global HUD scale (`:1410-1426`).
3. **User configuration and scripted/custom extension.** Custom gauges combine the common placement controls with a name, text, legacy semantic gauge type and animation (`fs2open:code/hud/hudparse.cpp:1618-1800`). A scripting gauge is only a named, initially-active slot in that list; a Lua callback receives its draw interface at render time (`fs2open:code/hud/hudparse.cpp:5721-5736`, `fs2open:code/hud/hudscripting.cpp:21-34`). HUD colour presets are versioned per-gauge RGBA files, with legacy IDs translated to string IDs and built-in colour inheritance applied before custom overrides (`fs2open:code/hud/hudconfig.cpp:1633-1778`). Separately, IFF data defines both ordinary and accessibility colours, including observer-relative team mappings (`fs2open:code/iff_defs/iff_defs.cpp:495-536`, `:737-780`). That separation is important: a palette can describe a team relationship without defining hostility.

Rendering is an **ordered gauge-array walk**, not a retained scene graph. The normal HUD and each cockpit display make separate passes; each visible gauge gets preprocessing/update, canvas/visibility checks, clip/font setup and then its virtual render (`fs2open:code/hud/hud.cpp:2076-2169`). Drawing helpers repeatedly set/reset screen scale, colour, clip and bitmap state (`fs2open:code/hud/hud.cpp:911-987`, `:1029-1143`). This is flexible and instrumentable, but it is not evidence of a texture-atlased, single-batch HUD. No SCP frame-time numbers were gathered, so “per-frame cost” here means the visible work: O(enabled gauges + emitted primitives), per-gauge state churn, and extra render-target passes for cockpit displays.

### 1.2 AllegianceCore today

AllegianceCore already has the right semantic boundary. `HudElement` carries availability, visibility, native/projected placement and nullable values; `HudElements` is a coverage inventory, not a drawing instruction list (`src/Allegiance.ClientCore.Game/Rendering/HudElements.cs:3-18`). `HudModel` is graphics-independent and both styles consume it. Classic and Modern are still selected by an enum with style-dependent defaults in persisted settings (`src/Allegiance.ClientCore.Game/Rendering/HudSettings.cs:6-16`, `:53-80`).

The shared `HudRenderer.Draw` is a long, deliberately ordered composition: indicators and selection, radar labels, training/console, target/inventory, additive Classic gauges, own status and final warp flash (`src/Allegiance.ClientCore.Game/Rendering/HudRenderer.cs:186-553`). Additive centre indicators and Classic gauges require batch transitions, while Modern substitutes procedural art (`src/Allegiance.ClientCore.Game/Rendering/HudRenderer.cs:442-466`; `src/Allegiance.ClientCore.Game/Rendering/ModernHudRenderer.cs:111-175`). Consequently **render order and blend-pass boundaries are compatibility data**, not incidental implementation details.

Current scaling is also intentionally unlike SCP's base-resolution stretch. Modern uses desktop density × user size, capped by the window's authored 1.5-units-per-1080px budget; cluster and pane scales derive from that one core (`src/Allegiance.ClientCore.Game/Rendering/ModernHudScale.cs:40-83`). Classic keeps native fixed-pixel artwork. P972 already proposes versioned skin JSON, load-time validation, immutable pre-bound resources and direct widget references, with zero JSON/file/dictionary work in `Draw` (`docs/reports/UI_SKINS_P972.md`, §2.1–2.3 and §2.8). It also already inventories all 111 HUD parity rows and both-style/all-skin proof requirements.

### 1.3 What to adopt concretely in the P972 definition

**Adopt the simple 80%: semantic gauge list + anchors + scale per resolution.** Extend P972's proposed schema conceptually as follows (illustrative data shape, not SCP syntax or implementation):

| Field group | Recommended meaning | Boundary that prevents SCP-scale complexity |
|---|---|---|
| `widgets[]` | Stable semantic IDs (`own.hull`, `target.range`, `radar`, `chat`, etc.), compiled renderer ID, enabled/presentation default, explicit draw-pass ID | IDs map to `HudElement`/shared model values. A skin cannot invent telemetry, contact eligibility, targeting or warning state. No arbitrary type names. |
| `layouts[]` | A small ordered set of base logical sizes (initially 1920×1080 and 800×480), optional aspect class (`standard`, `wide`), and safe-area rectangle | Exact viewport matching/fallback is deterministic and computed on resize. Do not reproduce SCP's many min/max/pruning/legacy-resolution special cases. |
| `placement` | Nine edge/corner/centre anchors or `projected`; normalized 0–1 origin within the safe area plus logical-pixel offset; width/height constraints | Keep `HudAnchor` and native y-up/projected y-down conversion in one adapter. Projected gauges never slew. Absolute per-widget sub-offsets are allowed only where art requires them. |
| `scale` | Independent `geometry`, `text`, `stroke`, with min/max and one inherited Modern core scale | Preserve Classic fixed pixels and P833/P859 exactly. Do not stretch X/Y independently or replace density sizing with viewport-height scaling. |
| `passes[]` | Named order such as `worldIndicators`, `radar`, `console`, `target`, `instrumentsAdditive`, `status`, `finalFlash`; blend mode declared in compiled renderer | The file orders known passes but cannot arbitrarily interleave target-preview or additive draws. Pixel goldens pin the result. |
| `palette` | Semantic text/accent/warning roles plus relationship/side mappings and an accessibility variant | Side colour is not an IFF/hostility rule. Native fixed colours remain separate tokens; shape/text redundancy survives every palette. |
| `resources` | Font/art roles and optional bounded pre-rendered variants | Resolve once on load/switch; no per-frame file lookup, parsing or resource construction. |

Resolution selection should be **authored breakpoint + deterministic fallback**, not “nearest resolution” guessed independently per widget: choose the last layout whose minimum logical height/aspect class matches, then scale uniformly and letterbox the safe area. Cache the fully resolved rectangles, text metrics and renderer/pass array on skin/viewport/density/size change. At 800×480 use a deliberately compact layout; at 4K rasterize at physical density. A per-ship override is not useful for Allegiance's native HUD and should not be in phase 1. If a future non-native cockpit skin needs one, make it a *skin-selected variant over the same shared model*, never ship-stat-driven gameplay UI; tag it `visuals.hud.perShipLayouts` (default off).

**What not to copy as an idea:** legacy gauge-ID translation layers, dozens of per-gauge parser handlers, arbitrary custom gauge semantics, cockpit render-target plumbing before there is cockpit art that needs it, unrestricted Lua drawing, and a general drag-anything editor. P972's 111-row coverage contract is stronger than a file that merely parses. Also do not turn every native art offset into public mod API: that creates hundreds of compatibility constraints without improving a skin.

### 1.4 Recommended slices, flags, cost and risk

1. **P972 phase-1 data extraction (parity-safe; no new visual flag).** Add only widget IDs, ordered passes, anchors and two layout records while extracting current Classic/Modern values verbatim. Verify decoded-RGBA equality for every existing scenario/resolution/style, including batch order and native text baselines. CPU/GPU: expected neutral after binding; no added fullscreen passes or per-contact draws. Require 0 B skin-selection allocation and no >2% p95 frame regression in the eventual rig A/B. **Cost M; risk high** because frame ownership and Classic additive composition are easy to disturb.
2. **Optional validated user layout packs (`visuals.hud.customLayouts`, visual-only, default off).** Allow only the bounded schema above, loaded outside `Draw`, all-or-nothing fallback to the prior skin. No scripts, file includes, reflection, gauge visibility rules that remove required parity elements, or hit-test rectangles independent of draw rectangles. GPU: same number of widgets and primitives as the selected built-in skin; reject additional fullscreen passes and cap contacts/labels through the existing shared policy, so 200v200 cost remains the built-in layout's cost plus no pack-specific pass. **Cost M; risk M** (validation and long-term schema support).
3. **Named palette/accessibility variants (`visuals.hud.paletteVariants`, visual-only, default off).** Adopt SCP's ordinary/accessibility split and observer-relative mapping, but source side/relationship from Allegiance's model; never import its team-attack table. Apply the same mapping in Classic, Modern and every later skin without changing contact sets. GPU: zero additional passes/draw calls; only constant colour changes, including 200v200. **Cost S–M; risk M** because hue-only remapping can destroy native side identity or warning contrast.
4. **Modern 2.0 and Jet data layouts (`visuals.hud.modern2`, `visuals.hud.jet`, each visual-only, default off).** Their renderer IDs remain compiled; data supplies composition rather than executable behaviour. GPU: no fullscreen blur/glow, no extra target preview and no extra contact enumeration; reuse current label cache/declutter. At 200v200, require the same native allowed-set, bounded ordinary labels in Tactical/Combat and stable frame p95 versus P972's pre-change baseline. **Cost L each; risk L** due complete HUD/screens coverage, not JSON itself.
5. **Do not adopt Lua HUD hooks.** A bounded declarative “text + existing value + gauge art” custom widget could be considered later under `visuals.hud.customWidgets` (default off), but it must use a whitelist of already available `HudElement` values and cannot call world/session APIs. Even that is low value until P972 ships. GPU would be capped to a small fixed primitive/text budget per frame and forbidden in the contact loop; arbitrary script drawing has unbounded CPU/GPU and security/compatibility risk. **Cost L; risk high; recommendation: reject for now.**

The key lesson is therefore not “make the whole HUD scriptable.” It is **make layout replaceable while semantics, visibility, render-pass invariants and performance budgets remain compiled and testable**.

## 2. Multiplayer netcode — borrow measurement and buffering discipline, not a second relevance system

### 2.1 SCP object updates, priority and bandwidth

SCP's object-update record is selectively flagged: pose/orientation, fuller physics, hull, shields, subsystem state/animation, AI, afterburner and support-ship data are independent categories (`fs2open:code/network/multi_obj.cpp:174-185`). Per-recipient/per-ship history suppresses unchanged values, with a special rule that non-perfect shields keep refreshing (`:56-83`, `:2417-2478`). Position is not necessarily sent when stationary; target and in-cone status can nevertheless force it (`:2386-2407`). Percent fields are byte-quantized, and optional fields are included only when their category is present (`:1238-1243`, `:1353-1378`). This is a **field-dirty + cadence** design, not a full immutable world snapshot per recipient.

Cadence depends on the recipient's selected update level, whether the subject is the target or another player, distance band, and front/rear view cone. The target tables run from 20–66 ms, player tables 20–100 ms, while rear/far AI can be 200–2500 ms (`fs2open:code/network/multi_obj.cpp:192-205`, `:212-283`, `:2272-2316`). The source itself says these values were not scientifically tuned (`:207-211`), so the numbers are not a recommendation. Targeted and player ships sort ahead of other ships, then front-facing and nearer subjects (`:997-1038`, `:1040-1110`). Updates stop for that pass when the recipient exceeds a byte budget (`:2486-2591`). Low/medium profiles cap at 1800/3400 bytes per granularity interval, high is effectively uncapped, and a server total is divided among connections (`:2916-2934`, `:3062-3108`, `:3123-3175`). A separate `MULTI_RATE` facility keeps five per-frame/per-second samples by named byte type for diagnostics (`fs2open:code/network/multi_rate.cpp:19-53`, `:77-123`, `:126-182`); it is not the enforcement algorithm.

**200v200 implication:** this is relevance/cadence scheduling, but not fog-of-war relevance and not a fixed global object quota. Every eligible ship is still considered per recipient, and sorting every list can cost O(recipients × ships log ships). At 400 ships its distance/view priorities could save egress, but repeatedly classifying/sorting and retaining recipient×subject history becomes server work and memory. AllegianceCore must also not let a camera-facing decision alter native discovery or targeting information.

### 2.2 SCP interpolation, time, join/respawn/turrets and standalone

The interpolation manager holds at most four timestamped physics snapshots per object and inserts newer frames in sorted order, dropping duplicates (`fs2open:code/network/multi_interpolate.h:9-29`, `fs2open:code/network/multi_interpolate.cpp:187-247`). With a bracket it linearly interpolates position, velocities and orientation; without one it runs ordinary physics, limits a catch-up step to 0.25 s, and later synthesizes a boundary sample to smooth the return to interpolation (`fs2open:code/physics/physics_state.cpp:5-13`, `fs2open:code/network/multi_interpolate.cpp:52-163`, `:250-266`). This is a useful state machine—**interpolate inside known history, extrapolate only outside it, blend on recovery**—but its linear blend is not inherently better than AllegianceCore's existing Hermite curve.

Time is a local mission clock plus an explicit skip. A late join seeds that skip once from server mission time; the join path also adds half average ping (`fs2open:code/network/multi_time_manager.cpp:9-21`, `:58-77`, `fs2open:code/network/multi_ingame.cpp:1816-1825`). Object packets carry shared frame/time headers (`fs2open:code/network/multi_obj.cpp:2498-2510`). This is not a continuous PLL or offset/RTT uncertainty estimator. In-game join itself is a staged reliable protocol: mission signature/load, ships, wings, post data/settings, jump, then ship choice, with repeated hull/shield refresh while choosing (`fs2open:code/network/multi_ingame.cpp:59-84`, `:114-250`, `:1869-1885`). Respawn requests/broadcasts are reliable and recreate the ship/loadout while resetting object-update history (`fs2open:code/network/multi_respawn.cpp:329-361`, `:587-710`). The turret manager is a small latest-due-packet queue keyed by parent/subsystem and a deduplicated outgoing subsystem queue (`fs2open:code/network/multi_turret_manager.cpp:5-54`, `fs2open:code/network/multi_turret_manager.h:55-97`). The standalone excludes its pseudo-ship from updates and runs multiplayer processing without making that object a player (`fs2open:code/network/multi_obj.cpp:1060-1070`, `fs2open:code/network/multi.cpp:1156-1190`).

SCP also has rollback primary-fire history: a ring of poses/velocities/orientations per ship is rewound, shots are simulated forward, then live poses are restored (`fs2open:code/network/multi_obj.cpp:46-54`, `:627-741`, `:777-853`). This is a game-rule/hit-registration decision, not a networking optimization to import casually.

### 2.3 AllegianceCore's current pipeline and scale evidence

AllegianceCore already ports native's target promotion, heavy/light split and deviation ageing. Selected heavy poses reset deviation; light and skipped subjects accrue different increments, with a target slot and a minimum heavy share (`src/Allegiance.Server/Server.RankedPose.cs:37-65`; native `FedSrv/FedSrv.CPP:3841-3950`, `:4141-4189`). A viewer pose floor prevents starvation (`src/Allegiance.Server/Server.RankedPose.cs:80-84`). Optional interest tiers add distance/cell classification, but are default off and are not part of the winning baseline (`src/Allegiance.Server/Server.InterestTiers.cs:219-237`, `:244-292`). SCP's view-cone/range scheduler should therefore **not** become another always-on relevance layer.

The production pipeline captures detached immutable per-tick deliveries, shares heavy/light encoding where possible, memoizes event/pose bytes, and publishes through a bounded worker (`src/Allegiance.Server/Server.BroadcastSnapshot.cs:11-26`, `:89-178`). Keyed streams coalesce while key-zero reliable events retain order; stale streams are shed only under the tick-gap/lane rules (`src/Allegiance.Server/BroadcastSnapshot.cs:118-162`, `:257-282`). P899's local 200-client real-TCP baseline used 20 Hz, immutable snapshots, encode-once, parallel build, native updates/GotoPlan and pool transport; it measured about 1.79 MB process allocation/tick and 78 KB publisher allocation/tick, with overlapping before/after timing ranges (`docs/reports/P899_REPORT.md`, “Loopback measurements”). P968 separately proved the optional pending-stream index removes a quadratic scan but left it default off pending rig A/B (`docs/reports/PUBLISHER_STREAM_INDEX_P968.md`, “Measurement first” and “Gate and A/B handoff”). These are stronger starting points than replacing transport with SCP-style object packets.

The client has two deliberately separate remote representations. Native-parity `ShipDeadReckoner` replays the real flight model from each heavy update, with a 1.5 s cap and no hot-path buffer allocation (`src/Allegiance.ClientCore/Flight/ShipDeadReckoner.cs:58-73`, `:172-204`, `:242-294`). Experimental, default-off Hermite rendering keeps eight samples, adapts delay to measured cadence (30–750 ms), interpolates only within history and falls back to reckoning past the newest sample (`src/Allegiance.ClientCore/Flight/RemoteShipHermiteInterpolator.cs:8-18`, `:50-100`, `:152-205`). Gunnery/lead still uses authoritative latest state, not the delayed render pose. The shared own-ship server clock is re-anchored by PING samples and integrates time-scale changes (`src/Allegiance.ClientCore/Flight/OwnShipServerClock.cs:9-23`, `:34-75`). Hermite currently timestamps arrival on the local render clock and drops non-increasing arrivals (`src/Allegiance.ClientCore/Flight/RemoteShipHermiteInterpolator.cs:101-123`), so SCP's sorted remote-timestamp buffer addresses a real remaining gap.

Join/reconnect is already a native-message join burst, not an SCP file-sync session. Reconnect grace is independently default off and replays MISSIONDEF/JOINED_MISSION/player/sector/export state to resynchronize (`src/Allegiance.Server/Server.ReconnectGrace.cs:217-345`; `src/Allegiance.ClientCore/Session/ConnectionSession.cs:1353-1439`). Native turret relay is a one-shot last-update kind, not SCP's latest-due turret queue (`src/Allegiance.Server/Server.Broadcast.cs` and native `FedSrv/FedSrv.CPP:3774-3796`, `:4049-4071`). Respawn rules likewise remain native mission/eject/relaunch rules, not SCP's respawn-point system.

### 2.4 Worth trying, with decisive rig metrics

1. **Per-category/per-peer byte and update-age telemetry (parity-safe; `profiler.broadcastBudget`, default off).** Add cheap counters for heavy/light/other keyed/reliable offered bytes, records, oldest subject age and dropped/coalesced streams, aggregated over five windows like SCP's diagnostic idea but without per-frame `memmove`. No send decision changes. At 200v200 and 400 peers, identify whether CPU, publisher backlog, transport queue or actual egress is binding before changing cadence. **Cost S; risk low.** Decide instrumentation by <1% tick p95 overhead and zero wire-byte/order delta with the flag on versus off.
2. **A byte-budgeted native-deviation experiment (flag-only (non-parity); `broadcast.nativeByteBudget`, default off).** Keep native target promotion, heavy/light semantics, visibility, deviation order and reliable lanes. Charge actual packet bytes against a per-peer window; if capped, defer only ordinary remote records and increase their deviation exactly as a skip would. Reserve own/source, target, parent, turret and reliable events; never divide bandwidth equally without preserving those classes. Do **not** add SCP's camera cone or its 200/600/1400 m thresholds, and do not combine this with rejected interest tiers. **Cost M; risk high (starvation/corrections).** On the rig baseline, alternate A/B/A/B at 200v200 and 400 peers. Adopt only if egress and tick p95/p99 improve without worse p99 update age, remote correction distance, own/target age, dropped reliable frames (must remain zero), join latency or bot combat outcome; include unbacklogged and WAN-shaped clients.
3. **Remote-timestamp ordered Hermite history (`visuals.remoteTimeline`, visual-only, default off; native reckoner remains default).** Feed heavy-update server time converted through the existing session clock, sort a bounded eight-sample buffer, accept late/out-of-order arrivals, and retain the current adaptive delay/fallback. Keep aim, targeting, collision, commands and bot decisions on latest authoritative state. **Cost M; risk M.** Replay identical 2/5/10/20 Hz streams with jitter, reordering, duplication and 0.25–1.5 s stalls; decide by correction step/jitter, time spent extrapolating, lead-pose error versus recorded truth and added render lag. GPU: identical ship draw count/materials at 200v200; CPU must stay bounded to eight samples/ship with no per-frame allocation, so no meaningful UM690 GPU cost is expected.
4. **Paced join-burst scheduling only if telemetry proves a spike (flag-only (non-parity); `broadcast.joinBurstPacing`, default off).** SCP's staged acknowledgements are not a reason to redesign the protocol, but they suggest measuring stage cost. Preserve the exact reliable message sequence and mandatory initial state; pace only optional repeated/background refresh work after the client can join. **Cost M; risk high.** Verify byte-for-byte stage transcripts, reconnect/wrong-token/name-collision cases and multiple rotations, then rig A/B 400-peer join/death surges for tick p99 and publisher lag versus time-to-playable. If required messages must be delayed to make a difference, reject the experiment.
5. **Do not adopt SCP rollback or respawn/turret policy.** Rollback hit registration would change native combat and multiply collision/simulation work under a 400-ship rewind: any future research must be a separate flag-only (non-parity) task with authoritative anti-cheat analysis, never a netcode cleanup. The current native turret one-shot and Allegiance pod/relaunch flows are parity surfaces, so SCP's alternatives have no adoption value here.

The highest-value lesson is **measure per recipient, bound history, and make overload policy explicit**. AllegianceCore should retain encode-once/pool/native-deviation as the baseline and test only narrow changes against it.

## 3. AI — use explicit goals and tactical overlays to simplify the bot driver, never to change server NPC law

### 3.1 SCP's goal, wing and combat model

SCP stores five mission/player goals per ship plus a separate dynamic-goal sentinel (`fs2open:code/ai/ai.h:99-101`, `:326-327`). A goal records origin, mode/submode, issue time, 0–100 priority, target and mode-specific payload (`fs2open:code/ai/aigoals.h:27-44`, `:47-85`, `:120-153`). Allocation prefers an empty slot, never preempts the executing goal merely to find space, otherwise replaces the oldest non-active entry (`fs2open:code/ai/aigoals.cpp:822-862`). Validation removes satisfied/impossible goals and holds unknown ones; sorting prefers achievable goals, explicit override, higher priority, then newer issue time. Goal zero becomes active (`:2338-2419`, `:2484-2530`). This is less a recursive “stack” than a **bounded, prioritized goal set with hold/resume semantics**. Wing orders fan out to member goals and wing completion removes matching mode/submode/priority/target entries (`:407-477`, `:994-1015`).

Combat has a second, faster mode/submode machine. Chase includes attack, squiggle, brake, evade, avoid, weapon evade and get-away variants, with timed/geometry-driven transitions (`fs2open:code/ai/aicode.cpp:9052-9067`, `:9244-9287`, `:9320-9367`, `:9448-9496`). Recent threat and range can trigger lateral thrust (`:9291-9317`). Guard gives a bomb threatening the protectee first priority, then hostile ships, then relevant environmental threats (`:10823-10853`). This separation is the transferable design: a long-lived objective need not be destroyed by a short evasive manoeuvre.

Formation slots use a custom formation or default leader-relative offset. Spread grows with the largest relevant hull radius, leader speed and formation scale, then rotates into the leader's frame (`fs2open:code/ai/aicode.cpp:12691-12752`). The controller predicts the formation point from leader velocity, relaxes aggressive formation keeping for a chaotic human leader, uses afterburner for large errors and speed matching nearby (`:12832-12851`, `:12902-13056`). Dynamic formation slots are compacted when a follower leaves (`:3745-3768`).

Difficulty is data at two levels. AI classes have accuracy/evasion/courage/patience and per-skill combat values (`fs2open:code/ai/aicode.cpp:649-699`, `:731-910`). Profiles supply five-skill arrays for aim/reaction/fire delays, turn scaling, movement choices, attacker/missile caps, damage/energy scales and many feature switches (`fs2open:code/ai/ai_profiles.h:27-103`). Parsing clones the base profile for a new named profile or edits a previous one, and `*-aip.tbm`/`*-msp.tbm` modules extend it (`fs2open:code/ai/ai_profiles.cpp:108-176`, `:805-849`). Some of these knobs alter damage, physics and scoring, so they are not suitable as AllegianceCore bot “skill” settings.

### 3.2 AllegianceCore's MCP bot driver

The MCP driver already has a strategic layer, a tactical target allocator and legal native controls. A fixed nominal 20 Hz decision loop prepares each bot's visible candidates and updates shared engager counts (`tools/allegiance-mcp/BotManager.cs:98-118`, `:1679-1908`). `CombatTargetSelector` prioritizes threats, then combat hulls, then miner/drone detachments; class caps bound pile-on and the default fills the most-engaged eligible target to cap, with a legacy spread switch (`tools/allegiance-mcp/CombatTargetSelector.cs:41-64`, `:108-199`). Its comments explicitly classify these caps/tiers as harness policy, not native wingman law (`:11-36`). Commander orders bypass autonomous selection.

Piloting uses the shared native obstacle dodge law before straight-line steering and suppresses gunfire while dodging (`tools/allegiance-mcp/BotManager.cs:2684-2755`, `:3189-3238`). Attack uses actual part ballistics and the shared lead solve, native-like throttle/fire bands, friendly-line suppression and legal afterburner/strafe controls (`:3195-3314`). Bot difficulty is currently only three environment values—accuracy, reaction delay and aggression—with absent values preserving normal behaviour (`tools/allegiance-mcp/BotDifficulty.cs:6-19`, `tools/allegiance-mcp/BotManager.cs:3201-3205`, `:3291-3300`). That is a useful seed for data profiles, but not a role/profile system.

At the strategic level, route wings, scouting, local/shared threat coordination and objective-specific drivers coexist across many `BotManager.*` files. Strike massing is a good example of why a simple formation port would be redundant: bombers already hold 3.5 km off a station, assemble a damage-computed requirement and release on a shared go time; late arrivals wait for the next wave (`tools/allegiance-mcp/BotManager.StrikeMass.cs:11-64`, `:395-483`). Support similarly prioritizes finale bombers/pushers, keeps repair-target hysteresis and drives ordinary observed repairs (`tools/allegiance-mcp/BotManager.Support.cs:37-91`, `:101-236`, `:336-410`). Any new goal model must preserve these proven policies rather than flatten them into generic “attack nearest.”

### 3.3 Bot-side ideas worth adopting

1. **A bounded strategic goal set plus a tactical overlay (parity-safe bot policy; `bot.goalStack`, default off for A/B).** Model at most five durable duties—human order, finale/strike, defend/protect, support/miner, travel/explore—with explicit priority, target identity/cookie, issued time and `Ready/Held/Complete/Abandoned`. Unknown fog state is `Held`, never completion. A short-lived `EvadeWeapon`, `DodgeObstacle` or `ClearFriendlyLine` overlay may own controls for a bounded interval and then resume the same strategic goal. Compile goal executors in C#; data selects existing IDs only. **Cost M; risk high** because scattered policy can regress finale/reconnect/order precedence. Verify golden decision traces for every current scenario before Live A/B, especially commander > finale > ordinary travel, no-target fog, dock/relaunch, death and rotation.
2. **Transit-only stable wing slots (`bot.wingFormation`, default off).** Use existing route-wing membership, not a new server wing concept. Assign deterministic slots and leader-relative offsets scaled by hull radius/speed; predict modestly from leader velocity, relax if the leader turns sharply, and abandon formation on combat, obstacle dodge, docking, standoff or human order. Do not move the proven 3.5 km strike hold into a generic formation. **Cost M; risk M.** Verify seeded geometry, follower removal/leader death, multi-sector routes and all flight styles; measure collision/dodge counts, p50/p95 arrival spread, objectives reached and never-parks versus the current driver. GPU: no extra rendering; at 200v200 CPU is O(wing size), not all-pairs.
3. **Observed-threat evade overlay (`bot.combatEvade`, default off).** Learn from SCP's timed submodes, not its thresholds: when the bot's own world reports an incoming missile or recent attacker, select a legal strafe/afterburner/chaff action for a short hysteretic window, then resume the goal. Only observed threats and mounted equipment are eligible; native lock, signature, weapon and cooldown rules stay server-side. **Cost M; risk M–high.** A/B identical seeded duels and full showcases for damage taken, survival, chaff use, objective time and firing uptime. Reject if it merely runs farther and produces prettier survival while lowering match completion.
4. **Versioned bot profile packs (`bot.profiles`, default off except the byte-equivalent built-in profile).** Move existing accuracy/reaction/aggression plus engager caps, target hold times, formation spacing and duty priorities into bounded supervisor-loaded JSON with source-generated serialization and per-field ranges. Supply named `showcase-normal`, `duel-rookie` and `strike-test` examples; log profile/version/hash in receipts. Per-skill arrays are fine, but **exclude** damage, turn rate, energy, cooldown, visibility, aiming server authority and other simulation knobs. No Lua and no runtime type names. **Cost M; risk M.** Validate whole-pack fallback, deterministic profile×seed decisions and unchanged default transcripts; run each affected bot suite three times and Live scenario comparisons.
5. **Protectee-centred threat priority inside the existing defense driver (`bot.protecteeThreat`, default off).** The useful guard idea is “ordnance/about-to-hit threat to the protected asset before a merely nearby fighter.” Add observed missile/bomber threats against the specific miner/station/bomber as a higher tier in `VisibleDefenseTargets`, retaining current engager caps and nearest tie-break. **Cost S–M; risk M.** Verify fog absence cannot create a target, expired observations age out, commander/finale orders still win, and measured miners/stations surviving do not reduce necessary strike escorts.
6. **Do not import SCP's profile surface or combat state machine wholesale.** Player-only damage reduction, max-player-homers, physics/energy changes and scoring flags are non-parity if applied to Allegiance's simulation and are unnecessary for bot quality. Generic circle/evade thresholds are a different flight/game scale. Likewise, SCP's nearest-target/global-attacker-cap model is not an improvement over the MCP driver's already coordinated cap/focus policy.

The best fit is **durable objective + interruptible tactical overlay + declarative policy values**. It reduces implicit state scattered across the driver while keeping all behaviour in MCP/bot code and all native server/NPC mechanics untouched.

## 4. Data-driven content and mods — modularize authoring and assets, not native session rules

### 4.1 SCP's composition model

SCP's generic modular-table loader enumerates a caller-supplied suffix in a caller-supplied order and invokes the same parser for every module (`fs2open:code/parse/parselo.cpp:5048-5076`; declaration defaults at `fs2open:code/parse/parselo.h:441`). Each subsystem chooses its suffix and base-first sequence: ships parse `ships.tbl`, then `*-shp.tbm`, followed by link/validation cleanup (`fs2open:code/ship/ship.cpp:6404-6429`); species parse base or built-in defaults then `*-sdf.tbm` (`fs2open:code/species_defs/species_defs.cpp:381-399`); HUD and AI profiles use their own suffixes. This is **ordered parser composition**, not one universal patch language.

Ship records show the useful authoring controls. A module can modify an existing class, decline to create a missing one, remove one, or clone a template/another ship before applying values (`fs2open:code/ship/ship.cpp:1915-2075`). List replacement is explicit in some fields rather than universally appending (`:2378-2404`). Post-parse cleanup repairs defaults, checks cross-record assumptions and resolves related data (`:6208-6333`). Species records similarly create or patch and then inherit their own earlier warp parameters; they cover presentation/resources (debris, shield/thruster animation, icons/sounds) plus gameplay-linked defaults such as IFF and AWACS (`fs2open:code/species_defs/species_defs.cpp:154-236`, `:281-369`). That mixture is convenient but means “species pack” is not automatically visual-only.

`game_settings.tbl` adds a minimum/target engine version check and mod title/version metadata before `*-mod.tbm` modules (`fs2open:code/mod_table/mod_table.cpp:227-275`, `:1782-1793`). A queried version then gates compatibility behaviour (`:1854-1860`). The useful idea is an explicit capability contract, not SCP's large collection of version-dependent booleans.

Models have separate world, HUD-target and tech-room assets, class-level old→new texture replacement, detail-distance tables and a separately selected collision LOD (`fs2open:code/ship/ship.cpp:2930-3044`, `:1086-1122`). Texture stems conventionally derive glow/specular/normal/height/AO/utility maps, with missing optional maps left absent (`fs2open:code/model/modelread.cpp:3210-3337`). Render LOD uses the model's closest point rather than merely its centre, applies detail/nebula multipliers, and clamps a selected level against model detail thresholds (`fs2open:code/model/modelrender.cpp:903-980`). This lets collision remain authoritative while visual detail changes—a boundary AllegianceCore should preserve.

### 4.2 AllegianceCore today

Static content is a named native core, not an overlay of arbitrary modules. `StaticCoreCache` prefers a binary and only its absence selects the adjacent text folder; corrupt binaries do not silently fall through. Text import validates and constructs a complete model before inserting the named cache entry, and consumers hold leases until retirement (`src/Allegiance.Core/Model/StaticCoreCache.cs:9-27`, `:46-84`, `:101-120`). The text version is native's 1337 sentinel, not a unique content hash (`:11-18`; native `Igc/missionigc.cpp:2390-2431`, `:2637-2675`). P908 explicitly leaves content hashing/distribution outside native join semantics (`docs/reports/P908_REPORT.md`, “Client decision for version 1337” and deferred items).

Client visual content already supports first-source-wins layering (`src/Allegiance.ClientCore.Game/Assets/LayeredAssetSource.cs:8-36`). The optional sky pack sits above native artwork with fall-through (`src/Allegiance.ClientCore.Game/Assets/AssetSources.cs:38-50`). The HD catalogue is more disciplined than a raw folder override: schemas 1–3 map native model/texture identity to materials, verify native hashes on demand, require accepted/complete entries and all maps, and fall back per material (`src/Allegiance.Core/HdPack.cs:4-24`, `:26-91`, `:93-130`). Per-atlas tuning is data, and mip selection is footprint/budget based (`src/Allegiance.ClientCore.Game/Rendering/HdMaterialRenderer.cs:130-143`, `:226-315`). Hull/civilization art selection is separately resolved from real native `ModelName` and side civilization, with explicit fallback (`src/Allegiance.Core/Content/HullModelResolver.cs:9-42`, `:85-137`).

For distance rendering, far ships collapse into one billboard batch per look key, retaining depth testing and side/light tint (`src/Allegiance.ClientCore.Game/Rendering/ShipLodSpriteRenderer.cs:22-40`, `:45-56`, `:99-135`). This is different from mesh LOD: it addresses hundreds of distant draw calls at 200v200, while the HD system addresses texture residency.

### 4.3 Recommended content architecture

1. **Deterministic, build-time core patch packs (parity-safe only when they express existing native record semantics).** Add a manifest-driven authoring layer over the existing text codecs, not a runtime stack of parsers. Fields: `schema`, `id`, `baseCore`, ordered `patches[]`, `requiredCoreSchema`, `features[]`, output version and content SHA-256. A patch can `create`, `updateExisting` (SCP's useful no-create idea), `remove`, or `instantiateTemplate`; reject missing update targets, duplicate IDs, cycles, invalid numbers, dangling references and incomplete required tables. Expand everything and validate the **complete resulting core**, then emit native binary + inspectable text + manifest. `remove` must list affected downstream references rather than silently deleting them. **Cost M–L; risk high** because native content identity is not version 1337. Verify byte/semantic round trips for every core, deterministic order independent of filesystem enumeration, malformed-pack rejection, server/client exact-pack startup and ordinary native play.
2. **A hive/race as a complete opt-in core plus a separate visual definition.** For a crystal-parasite hive, define its civilization, hull/station/part/development records and starting tech in that derived core, using only existing native rule fields for a parity-safe first slice. Put side colours, engine/shield/debris art, warp treatment, icons and sounds in a `RaceVisualDefinition` keyed by civilization ID **and core pack hash**. `visuals.race.hive` (visual-only, default off) controls only the latter; selecting the hive core is an explicit host content choice, never a client mod that changes rules mid-session. Any genuinely new parasite mechanic is **flag-only (non-parity)** under a separately specified `gameplay.hiveParasite` flag (default off, server-validated) and absent from the parity-safe core. **Cost L for ordinary content, XL for new mechanics; risk high.** Verify all production/research/purchase/dock/relaunch/bot paths with the hive, mixed native clients only when they have the same core, and media/license review. GPU: reuse existing hull/effect pipelines and far-sprite batching; cap animated engine/debris instances and texture residency. On UM690 at 200v200, use far-tier unanimated sprites and the same material budget as other races—no unique per-ship post-process or dynamic light.
3. **Versioned optional visual packs (`visuals.assets.hd` and `visuals.assets.sky`, visual-only, default off in the future unified settings; preserve migration of existing choices).** Generalize today's good hash/fallback rules into a small manifest with `requiredClientSchema`, native asset hashes, map completeness, review status and estimated resident bytes. Do not allow a pack to name core records, simulation constants or arbitrary paths. Native art is the fallback per material/file, never a blank model. **Cost M; risk M.** Verify missing/corrupt/stale/rejected packs and no-pack RGBA equivalence. GPU: account five-map PBR memory separately from basecolour-only mode; at 200v200 enforce the existing byte budget and footprint mips, with no additional fullscreen pass for pack presence alone.
4. **Projection-aware, hysteretic visual LOD (`visuals.shipLodBias`, visual-only, default off).** Learn from closest-point LOD, but use projected radius/pixels so FOV/aspect changes do not change the wrong threshold. Keep independent world/HUD preview/texture-mip choices and native collision geometry. Add a small enter/exit threshold band to avoid oscillation; keep the current look-key billboard fallback. **Cost M; risk M.** Verify pixel-footprint thresholds across FOV/aspect, no popping thrash, HUD target identity and unchanged collision traces. GPU: on UM690 this should reduce triangle/draw cost at 200v200, especially with far batches; texture memory can increase if mip bias is wrong, so record GPU draw count, estimated texture bytes and frame p95 and reject regressions.
5. **Do not implement live modular rule stacking or an engine-version flag museum.** Native clients negotiate a named core/version, not SCP's arbitrary mod capabilities. Every multiplayer pack must therefore be provisioned identically before join; an out-of-band hash/manifest can reject mismatch but must not pretend the native 1337 value proves identity. Keep compatibility to a few explicit schemas and features, not dozens of booleans that gradually recreate historical game rules.

The right split is **immutable native-rule content selected by the host, layered optional visuals selected by each client, and reproducible authoring pipelines for both**. SCP's modular authoring is valuable; allowing independent clients to patch live game rules is not.

## 5. Space look — camera-centred angular backgrounds, a bounded depth design and a measured “sim” preset

### 5.1 SCP's skybox and distant artwork

SCP supports an actual model as the background. The model has its own orientation, alpha, replacement textures and animation instance; it is rendered at `Eye_position` with the skybox flag and normally no depth buffer (`fs2open:code/starfield/starfield.cpp:2309-2350`, `:2352-2430`). Animation time is kept separately from mission time (`fs2open:code/model/modelrender.cpp:1370-1378`; timestamp reset at `fs2open:code/starfield/starfield.cpp:878-885`). Sun and background bitmap entries can also advance frames from their declared rates (`fs2open:code/starfield/starfield.cpp:1324-1337`, `:1517-1555`). This gives a stable orientation while the camera translates: the model follows the eye rather than the sector origin. It is not a giant object that the pilot can approach.

Point stars rotate as **directions without subtracting view position** (`fs2open:code/render/3dmath.cpp:172-178`). Suns use that same far-away rotation followed by projection and a screen-aligned quad of angular size (`fs2open:code/starfield/starfield.cpp:1274-1356`). Background bitmap vertices are authored on a sphere (radius 1000), with optional subdivisions, rather than being a screen-space quad stretched after projection (`:269-376`). The whole background pass disables depth (`:1940-1999`). These choices explain why looking sideways does not create the planar-far-clip appearance: infinite/background content does not participate in scene depth at all, and the sun/star direction does not swim with eye translation. There is no claim here that SCP's quad tessellation/UV mapping is intrinsically distortion-free at every aspect; its values should not be copied blindly.

Environment mapping renders six axis-aligned 512² views once and derives a 16² irradiance map. A supplied cubemap can avoid generation; background/model changes invalidate the cached maps, while dynamic/subspace mode makes targets dynamic (`fs2open:code/starfield/starfield.cpp:888-954`, `:3082-3101`, `:3103-3197`, `:3200-3208`). Static generation therefore costs six background renders plus irradiance on a sector/change boundary, not automatically six full-scene renders every frame. **Dynamic regeneration is a different, much higher-cost feature and should not be inferred from the presence of environment mapping.**

### 5.2 Exact projection/far-clip/depth comparison and the “look from aside” artefact

SCP's defaults are near = 1 and far = 1,000,000 (`fs2open:code/graphics/2d.cpp:359-364`). `gr_set_proj_matrix` constructs an ordinary finite perspective frustum from FOV/aspect/near/far (`fs2open:code/graphics/matrix.cpp:143-190`). Its depth coefficients are the conventional non-reversed mapping, with OpenGL [-1,1] and Vulkan [0,1] variants (`:52-71`). No infinite or reversed-Z scene projection was found in this path. Camera FOV supports separate default/cockpit values and asymmetric variants (`fs2open:code/camera/camera.cpp:17-19`, `:58-147`), while the ordinary projection factor is defined at `fs2open:code/render/3d.h:57`. The large far distance is still a **planar view-space-Z limit**, not radial distance. The background escapes it by depth disabling, not by a special radial clip.

AllegianceCore's flight cameras likewise use finite planar perspective projection (`src/Allegiance.ClientCore.Game/Rendering/CockpitCamera.cs:39-43`, `:75-83`). The brief's diagnosis is exact: at radial distance `r` and off-centre angle `a`, a point crosses the far plane when `r·cos(a) > far`. With the old 6000 value, an aleph 6000–8500 m out could be clipped straight ahead and become visible when turning brought it nearer the edge. **The current checkout already carries the separate fix:** the shared constant is 10000 and comments record the old 6000 behaviour (`src/Allegiance.ClientCore.Game/Rendering/ExternalCameras.cs:42-48`), and chase/cockpit/missile cameras all consume it (`src/Allegiance.ClientCore.Game/Game1.Lifecycle.cs:248-276`). Native sets world and poster clips to 10000 (`WinTrek/WinTrek.cpp:323-329`). This report therefore treats the 6000 issue as historical context, not a still-open task.

The current sky is already protected independently. `NativeSkyPlacement.SkyProjection` recovers FOV/aspect and uses near 1/far 80000; the dome, stars and planet are camera-centred and all sky tiers disable depth (`src/Allegiance.ClientCore.Game/Rendering/NativeSkyPlacement.cs:53-75`; `src/Allegiance.ClientCore.Game/Rendering/NativeSkyRenderer.cs:115-170`, `:177-243`). The default black tier has three finite parallax star shells plus native planet/moons/galaxies/sun, also under that projection and with no depth (`src/Allegiance.ClientCore.Game/Rendering/BlackSkyRenderer.cs:4-31`, `:94-134`). The HD tier reuses native globe topology with equirectangular star/nebula textures and native planet posters (`src/Allegiance.ClientCore.Game/Rendering/HdSkyRenderer.cs:4-34`, `:108-136`, `:177-213`). Thus AllegianceCore already has the most important SCP background invariant; there is no need to enlarge scene far to SCP's million.

**Best technique for any future >10000 object requirement:** keep native 10000 as the default. For an opt-in extended-range mode, do not substitute a radial CPU cull and assume it fixes clipping—the GPU projection still clips by Z. Either (a) draw a bounded far shell in a second projection/pass with appropriate depth handling (`visuals.depth.farShell`, default off), or (b) migrate the entire scene to reversed-Z/infinite projection while retaining depth-tested geometry and rendering the sky depth-free (`visuals.depth.infiniteReverseZ`, default off). Reversed-Z improves depth distribution but does not itself make off-axis objects legal under a conventional near/far clip; an infinite far mapping addresses that. Full-scene migration is high risk because custom linear-depth, volumetrics, flare occlusion, sprite depth and clear/compare states must all be audited. GPU cost is essentially the same geometry/fill, but correctness risk is large. A far shell adds one projection/pass and far geometry only.

### 5.3 Lighting, tonemapping, bloom and the source of the “sim vibe”

SCP's named lighting profiles choose linear, Uncharted, two ACES variants, Cineon, two Reinhard forms or piecewise-power curves and expose exposure plus per-light brightness/radius adjustments (`fs2open:code/lighting/lighting_profiles.h:15-65`, `fs2open:code/lighting/lighting_profiles.cpp:274-389`). The default is Uncharted with exposure 4, overall-light multiplier 3.5 and inverse ambient multiplier 0.286 (`:397-446`). Those values belong to SCP's content/light units and must not be transplanted. The tonemap uniform carries exposure, algorithm and curve parameters (`fs2open:code/graphics/util/uniform_structs.h:253-271`), and the pass samples the HDR scene and writes display-referred output (`fs2open:code/graphics/opengl/gropenglpostprocessing.cpp:69-102`; shader dispatch at `fs2open:code/def_files/data/effects/tonemapping-f.sdr:208-250`). HDR10 output is a separate path, not a reason to enable an HDR monitor mode on the UM690.

Bloom starts at half resolution, extracts bright values, blurs horizontal/vertical twice over mip levels, then adds the result to scene colour before tonemapping (`fs2open:code/graphics/opengl/gropenglpostprocessing.cpp:105-207`, `:503-527`). Vulkan uses two half-resolution RGBA16F textures with four mips (`fs2open:code/graphics/vulkan/VulkanPostProcessingBloom.cpp:140-153`, `:317-414`). This is a real multi-pass bandwidth cost, not “free glow.”

AllegianceCore's bloom is already default off and deliberately smaller: thresholded bright-pass at half res, one horizontal and one vertical Gaussian blur, then composite; HUD draws afterwards (`src/Allegiance.ClientCore.Game/Rendering/BloomPostProcessor.cs:3-15`, `:89-122`). The scene target is 8-bit `SurfaceFormat.Color`, not a floating-point HDR target (`src/Allegiance.ClientCore.Game/Rendering/VfxPostProcessor.cs:76-89`). The PBR shader has its own hue-preserving peak-channel tone curve in gamma space to avoid silver/desaturated native hulls (`src/Allegiance.ClientCore.Game/Shaders/NativePbr.fx:58-72`, `:106-118`). Therefore **copying SCP's global tonemapper today would be colour-wrong twice over:** the main scene is LDR, and PBR deliberately preserves native gamma-space colour. A proper global experiment needs a linear-HDR scene contract and a single output transform, with PBR's local curve made an explicit non-HDR/legacy path.

The requested “sim vibe” is a combination, not a magic ACES checkbox:

* filmic highlight roll-off with restrained exposure rather than clipping every emissive to white;
* slightly desaturated/neutral **world** grading while HUD relationship/warning colours stay unchanged;
* dark but detailed midtones and directional key/rim light, rather than high ambient wash;
* sparse, mostly neutral stars with varying brightness and no exaggerated near-star parallax;
* a small angular sun and limited glare, not a large additive white disc or bloom around all HUD elements;
* environment reflections that support materials but do not overpower the sector key light.

A reasonable **first experiment, after linear-HDR plumbing**, is ACES-approximate at exposure **0.9**, world saturation **0.85**, no tint/lift, threshold **1.2 linear** for bloom and bloom contribution **0.08**. Use native per-sector star counts or about 500 fallback points, grayscale brightness roughly 24–160/255 and no bright near shell. Keep the current small sun/flare angular footprint, start glare alpha around **0.25**, and flare only inside roughly the central 45° (`dot > 0.7` as an initial experiment, not a native rule). These are starting values for captures, not SCP constants or claimed final art direction. Compare against ACES-off/native and Uncharted at the same scene; a different content scale may require changing exposure once, not layering another curve on PBR.

### 5.4 Nebula and volumetrics

SCP's volumetric nebula bakes a watertight model into a small 3D occupancy/distance texture, with optional separately generated 3D noise. Defaults are 15 view steps, 6 sun steps, resolution/noise exponents 6/5, and detail settings scale step counts (`fs2open:code/nebula/volumetrics.h:18-76`, `fs2open:code/nebula/volumetrics.cpp:250-283`, `:403-585`). Its full-screen pass clips the ray to the volume and reconstructed scene depth, accumulates density/sun lighting and attenuated scene emissive colour (`fs2open:code/def_files/data/effects/volumetric-f.sdr:78-115`, `:139-210`; invocation/texture bindings at `fs2open:code/graphics/opengl/gropengldeferred.cpp:578-660`). This is an occupancy/noise raymarch, not an animated skybox texture and not a reason to simulate volumetrics on CPU every frame.

AllegianceCore already has the harder performance controls for raymarched explosions: coverage-based 48–510 step levels, full/half/quarter resolution, a nearest-volume cap, total pixel-step budget and frame-time adaptation (`src/Allegiance.ClientCore/State/VolumetricQuality.cs:29-69`, `:83-111`, `:155-190`, `:195-240`, `:276-320`). The missing feature is a **static nebula volume**, not budget architecture. A weak-iGPU implementation should reuse those controls rather than add an unbounded second full-resolution fog shader.

High colour/compatibility risk; measure GPU p95 and captures. |

The strongest immediate conclusions are: **retain the 10000 native fix and depth-free sky; reuse rather than replace the current camera-centred art; make static angular backgrounds cheap; and treat HDR/volumetrics/environment generation as separately budgeted features, not one giant “better graphics” switch.**

## 6. Quick scans

**Physics model.** SCP ramps commanded local velocity toward throttle/afterburner goals with different acceleration/deceleration constants, optional slide and glide behaviour, and temporary reduced damping after impulses (`fs2open:code/physics/physics.cpp:532-686`, `:687-759`, `:1057-1065`). AllegianceCore instead ports native's exponential drag, directional thrust clipping, afterburner boost and turn-torque law in one pure integrator used by server and dead reckoning (`src/Allegiance.Core/Sim/ShipKinematics.cs:87-200`; native `Igc/shipIGC.cpp:2852-3054`). These are different flight feels and network contracts: **do not adopt SCP damping/glide**. Any such experiment is flag-only (non-parity) under a separately scoped `sim.fs2FlightModel` flag (default off), with replay/flight-model proof and no reuse of the changed model for cosmetic effects alone. Cost L/high; no current value.

**Missile lock and tips.** SCP checks homing type, target/range/FOV/subsystem sight and EMP state, advances the indicator and transitions audio (`fs2open:code/hud/hudlock.cpp:595-731`); it can also iterate several lock records (`:282-370`, `:1530-1536`). Native Allegiance instead builds one mounted magazine's lock from off-bow angle, lock time and target ECM (`Igc/magazineigc.cpp:110-175`). AllegianceCore already maps the owner-only wire value into none/partial/full and emits native threshold tips once, including target-change suppression (`src/Allegiance.ClientCore/State/MissileLockFeedback.cs:19-52`; `src/Allegiance.ClientCore/State/ClientWorld.cs:5720-5729`). Keep that shared model in both HUD styles. Do not import multi-lock target acquisition or SCP's lock timing as a “tip improvement”; only the lock flower/animation may be reskinned under the active P972 skin's own `visuals.hud.*` flag (for example `visuals.hud.jet`, default off). Cost of an alternative rule: L/high, non-parity and unnecessary.

**Radar styles.** SCP offers standard 2-D, orb, BSG/DRADIS and an N-gon variant selected by the HUD parser (`fs2open:code/hud/hudparse.cpp:2958-3184`, `:1262-1269`; DRADIS's tilted geometry/sweeps at `fs2open:code/radar/radardradis.cpp:335-420`). Its blips retain range, brightness and visibility rules independently of those shells (`fs2open:code/radar/radarsetup.cpp:164-180`, `:293-369`). AllegianceCore has square/optional round native radar, native LOD/contact/label tiers and Modern-only declutter (`src/Allegiance.ClientCore.Game/Rendering/RadarLod.cs:4-39`; `src/Allegiance.ClientCore.Game/Rendering/RadarBracketRenderer.cs:298-363`; `src/Allegiance.ClientCore.Game/Rendering/HudSettings.cs:65-80`). An orb/DRADIS **renderer** is a reasonable later P972 skin, `visuals.radar.orb` or `visuals.radar.dradis` (visual-only, default off), only if it consumes exactly the existing allowed contacts, target/order/threat overlays and both-style/all-skin tests. GPU: one small radar viewport, but 3-D spheres/tilted discs can cost more than sprites at 200v200; use instanced flat icons and the existing label cap. Cost M/medium, value aesthetic rather than urgent.

**Lua scripting API.** SCP exposes a very broad live surface: mission objects/goals/wings, tables, graphics/cameras/post effects, HUD/UI, audio, controls, files and multiplayer, plus conditional hooks (`fs2open:code/scripting/api/libs/mission.cpp:178-203`, `:557-844`; `fs2open:code/scripting/api/libs/graphics.cpp:76-169`; `fs2open:code/scripting/api/libs/cfile.cpp:17`; `fs2open:code/scripting/scripting.cpp:80-107`, `:179-183`). This is powerful for a mature mod ecosystem but far too broad and dynamic for AllegianceCore's parity/AOT/security/hot-path requirements. Do not add a general Lua host for HUD, bots or server rules. Prefer versioned JSON + source-generated serializers, compiled renderer/goal IDs, bounded bot profiles and offline proof scripts. A future sandbox is a separate XL/high-risk design with capability limits and deterministic scheduling, not a P978 recommendation.

## 9. Native intent and modern approach

### Native intent

| Area | What native Allegiance actually does and must preserve |
|---|---|
| HUD | Native uses authored MDL gauge art, fonts, anchors and visibility gates, not a user script runtime. String images hang below their native point (`engine/image.cpp:354`, `:382-390`) and group children paint first-child-on-top (`:954-969`). The velocity indicator comes from real source velocity (`WinTrek/indicator.cpp:128-150`), centre/order indicators share camera gates (`:762-797`), and radar LOD/important-contact rules define the allowed information (`WinTrek/radarimage.cpp:703-710`, `:747-757`). Classic must preserve these semantics; a skin may only recompose them. |
| Multiplayer | Native ranks per-viewer ship updates, promotes the target, splits HEAVY/LIGHT and ages deviation (`FedSrv/FedSrv.CPP:3841-3950`, `:4141-4189`). Clients convert server time then replay real flight forward, including bounded correction (`Igc/shipIGC.cpp:3104-3297`). Guaranteed events and one-shot turret relay retain order (`FedSrv/FedSrv.CPP:3774-3796`, `:4049-4071`). Native has no delayed Hermite smoother or rollback-hit mandate. |
| AI | Native wingmen use nearest-different-side targeting rather than SCP's rich goal profiles (`Igc/shipIGC.cpp:2030-2057`), with native defend acquisition requiring a damaging primary (`:2680-2695`) and attack/dodge/fire bands (`:2356-2604`). Native Wopr/Pig bot strategies are external policy, not permission to change server NPC law. MCP finale, strike, wing, escort and miner policies must remain bot-side and observation-honest. |
| Data | Native chooses a named core, caches it, prefers binary and has a text fallback marked version 1337 (`Igc/missionigc.cpp:2390-2431`, `:2637-2675`). The client checks its local version before loading (`clintlib/clintlib.cpp:4212-4221`). There is no generic modular live-rule negotiation or content hash. New core content must use native record semantics unless explicitly classified non-parity. |
| Space | Native world/poster clips are 10000 (`WinTrek/WinTrek.cpp:323-329`). Stars are drawn at infinity (`effect/starimage.cpp:32-53`), globes are unlit sky geometry (`effect/efgeo.cpp:1029-1052`) and planets are poster billboards (`effect/efimage.cpp:515-563`). Native's old fixed-function material path has no modern PBR requirement (`engine/device3d.cpp:758`) and its lighting is not SCP's HDR pipeline. Visual additions must be optional and leave these native paths available. |
| Quick scans | Native flight is `ExecuteShipMove` (`Igc/shipIGC.cpp:2852-3054`), missile lock is the magazine's off-bow/time/ECM law (`Igc/magazineigc.cpp:110-175`), radar has four native LOD tiers and optional square/round presentation (`WinTrek/radarimage.cpp:2-18`, `:703-980`), and native bot scripting lives in external Wopr/Pig mechanisms rather than a general in-process Lua API. |

### Modern approach

AllegianceCore should take **contracts, not implementations**. P972 turns a shared semantic HUD into pre-bound, validated layouts while retaining native order and zero-delta Classic/Modern proof. Broadcast uses immutable detached snapshots, encode-once sharing and pooled asynchronous publication, with instrumentation before any default-off scheduling experiment. Rendering may use a bounded delayed timeline only as an opt-in visual smoother; aim and authoritative state remain separate.

The MCP driver can express durable goals and short tactical overlays in C# with versioned data profiles, but never moves those policies into server NPCs. Content is reproducible and complete at build time: native-rule cores are selected identically by server and clients, while optional visual packs are independently hashed, budgeted and able to fall back per asset. Space rendering keeps camera-relative angular backgrounds depth-free, uses static generation and existing pixel-step/LOD budgets, and treats HDR/environment/volumetrics as separate opt-in passes rather than a universal quality tier.

This yields the useful modern properties SCP demonstrates—data-driven presentation, explicit overload handling, prioritized durable goals, modular content and convincing space—without inheriting its non-commercial source, legacy protocol, game rules, scripting surface or unbounded GPU cost.
